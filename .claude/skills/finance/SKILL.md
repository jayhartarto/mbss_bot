# MBSS v2 — Finance/Scoring Conventions

This project is an IDX (Indonesian Stock Exchange) Sharia-universe trading-assist Telegram bot. It has TWO scoring layers that coexist — know which one a task touches before changing anything.

## Layer 1 — Core per-ticker score (`engine/scoring.py`, `compute_factor_scoring`)

- **Final score** = `Value×0.25 + Momentum×0.45 + Sentiment×0.30` (all 1-10 scale). This weighting is the UNIVERSAL formula also used by `/myportfolio` — don't reweight it for a single feature; reweight a *downstream* rank instead (see Layer 2).
- **Adaptive scoring convention**: RSI/volume/EMA-distance are NOT scored against fixed thresholds — each stock is scored against its OWN trailing history via `core.percentile_rank(series, value)` (0-1) → `core.score_from_percentile(pct)` (maps to 1-10). Needs `MIN_HISTORY_FOR_ADAPTIVE = 120` trading days (~6 months); falls back to fixed bands below that. Reuse this pattern for any new adaptive score — don't invent a fixed magic-number threshold when percentile-vs-own-history is available.
- **ADX** (trend strength, not direction): `<20` weak/sideways, `20-25` neutral, `>=25` strong (`format_adx_label`, `calculate_adx`). Momentum score is damped toward neutral when ADX<20 (untrustworthy trend signal).
- **CMF** (money-flow direction, -1..+1): `>0.15` clearly positive, `<-0.15` clearly negative — used both as a sentiment_score nudge (`cmf_adjustment = cmf * 2.0`) and as a gate condition elsewhere (Bollinger band-walking, whitelist net-buy/sell penalties).
- **RSI**: NOT scored directly — used only as an overbought FILTER via the adaptive p75 threshold, capping momentum_score at 7.0. Oversold is never penalized (can be a genuine entry opportunity on swing horizon).
- **Action tiers** (`decide_action`, `ACTION_RANK`): `STRONG_BUY` final≥7.5, `BUY_ACCUMULATE` ≥6.0, `HOLD` ≥4.5, else `AVOID_SELL`. Hard ceilings override the tier (never just adjust it): financial distress or bearish chart pattern → cap at HOLD; overbought/bearish OBV divergence/volume-spike-anomaly/MACD bearish cross → cap at BUY_ACCUMULATE. `MIXED_SIGNALS` fires when components strongly disagree (spread≥4.0) or the score sits within 0.3 of a tier boundary while a soft risk flag is present — surfaces genuine tension instead of false precision.
- **HIGH CONVICTION** (`compute_high_conviction_score`, 7-8 Minervini/IBD-style criteria: tight 5d consolidation, breakout-close confirmation, 4H candle body strength, relative volume, avg volume, near-10d-high, above EMA9+SMA20). Threshold: `met >= max(5, round(checkable * 0.7))` — self-adjusts when a data source is unavailable (checkable shrinks, threshold shrinks with it). Adding a new criterion here is safe (same accounting pattern) but ONLY if the candidate is realistically "already breaking out" — a pre-breakout signal (see Bollinger squeeze) does NOT belong here, it needs its own separate section (real case: squeeze candidates fail near_high/breakout_confirmed almost by definition).
- **Bollinger Bands** (SMA20±2σ, computed in `compute_factor_scoring` and `compute_intraday_targets`): `%B = (price-lower)/(upper-lower)`, `<=0.1` near lower band, `>=0.9` near upper band. Band-touch mean-reversion bonus to sentiment_score is GATED by trend regime (ADX≥25 + `is_below_ema21` direction) to avoid misreading "band walking" (price riding one side of the band during a strong trend — continuation, not reversal) as a reversal signal. Squeeze = bandwidth `(upper-lower)/mid` at ≤20th percentile of its own ~120-day trailing history — a PRE-breakout signal, kept as an informational field (`bollinger_squeeze`, `bollinger_bandwidth_percentile`), never gated into HC's threshold.
- **RR (risk:reward)**: `targets.risk_reward_at_max` is computed at `target_buy_max` (the top of the suggested pullback entry zone) — this UNDERSTATES real risk once price has already run past entry_max, which it often has by the time anyone reads the pick. For anything ranking/gating "if I buy right now," use `engine/backbone.py`'s `compute_rr_at_current_price(scoring)` instead (RR at last close). Never silently swap this in `targets` itself — other features (`/check`, `/myportfolio`) depend on `risk_reward_at_max`'s existing meaning.
- **Smart money / Bias Bandar**: `SMART_MONEY_BROKER_WHITELIST` = 13 broker codes (ZP, AK, BK, YU, AI, SQ, BB, KZ, RX, RF, DX, HP, KI). `whitelist_accumulation_net_pct` / `whitelist_num_brokers` are computed FREE during `/eodscan` from the nightly whitelist sweep (already-fetched RapidAPI data, zero extra cost) and already feed the core score via Bias Bandar penalties (DISTRIBUSI -1.5/-3.0, TANPA DUKUNGAN -1.0/-2.0, since v3.16.0) — this is an established, already-live signal, not an untested one. `±15%` net with `>=2` brokers is the standing "meaningful" threshold used everywhere this field gates something (accumulation-candidate sections, backbone danger/probability, consensus tags).

## Layer 2 — AB-RC1 Backbone (`engine/backbone.py`, `engine/market.py`)

Source of truth: `backtest/MBSS_v317_AB_RC1_Final_Implementation_and_Research-1.md` (user's backtest research doc). Computed ONCE per night in `run_nightly_full_scan`, cached as `backbone_daily`, consumed by `/hc`, `/screendaytrade`, `/consensus`, `/check`.

- **Market regime** (`engine/market.py`, `classify_market_regime`): R1 Bull Stable / R2 Bull High Vol / R3 Sideways / R4 Risk Off / R5 Stress / R0 Unknown. Driven by today's breadth (% advancing), today's IHSG return, and IHSG volatility PERCENTILE (adaptive vs its own trailing history via `get_ihsg_volatility_percentile`, same percentile-vs-own-history convention as Layer 1) — the volatility dimension is what splits R1 from R2 (return+breadth alone can't).
- **Danger Gate** (`compute_danger_score`, 0-100, higher = more dangerous): base = `100 - v5["risk"]["score"]` (reuses the already-tuned `_score_breakout_drop_risk_v4`, covers MACD/ADX/liquidity/dist-to-high/vol_ratio/CMF/RSI/RR/fade/ret1) PLUS additive penalties for what that base doesn't cover: Room, cross-sectional day-range-volatility percentile, post-ARA/extreme-single-day-move (`ret_1d_pct>=20%: +20, >=12%: +10` — blunt proxy for "just hit auto-reject-atas," a real observed failure mode: a stock can look excellent on continuation/CMF/volq the day after limit-up while actually being a chase-risk setup), bearish OBV divergence, MACD bearish cross, below-SMA50-AND-EMA21 (compounding), near-price-floor, financial distress, whitelist net-sell (`<=-15%`, `>=2` brokers), and regime routing (R4/R5/R0 add a flat penalty). REUSE philosophy: only add what the base v4 score doesn't already check — don't re-derive from scratch.
- **Danger Gate cutoff**: a CROSS-SECTIONAL quantile over TONIGHT's own universe of candidates, not a fixed absolute score — `DANGER_GATE_QUANTILE_BY_REGIME` (R1=0.55 most permissive, tightening through R5=0.15). Only R1's cutoff has real forward-validation behind it (all the doc's August simulation dates were R1) — others are deliberately conservative placeholders pending forward data. Don't loosen them without new evidence.
- **Probability Rank** (`compute_probability_score`, 0-100, higher = better): weighted blend — continuation 15%, CMF 10%, ADX-reliability 10%, relative-strength-vs-IHSG 15%, Bollinger context 5%, Safety(v5 risk) 15%, VolQ 10%, Room 5%, RR-at-current-price 15% — plus a small regime-compatibility nudge. RR's weight was raised from an initial 5%→15% after a real observation (all early Top-8 picks had RR<1 without it) — this is exactly the kind of after-the-fact correction that should ONLY happen from a concrete observed failure, never a hunch; log the reason when you do it.
- **Entry Rank**: `entry_rank`/`entry_rank_total` assigned to EVERY Danger-Gate survivor (not just Top-8), ranked by probability_score descending — this is the UNIVERSAL number shown consistently in `/hc`, `/screendaytrade`, `/consensus`, `/check`. Rank does NOT reorder by danger — danger only gates (pass/fail) before ranking; two survivors with very different danger scores can still rank purely by probability. Lower rank number = better; check `predicted_danger` directly for "which is safest," not rank.
- **filter_to_gate_survivors**: the pool fed to `/screendaytrade`/`/hc` is ALL gate survivors (~1/3 of the universe typically), NOT the narrow Top-8 — narrowing to Top-8 would make both tools nearly duplicate each other and destroy SDT's "find things outside HC's radar" role. Top-8 itself is reserved for Consensus Prime / Explosive Lane search space.
- **`/consensus` structure** (doc §6-7, fully deterministic, no Gemini narrative): Consensus Prime = exact intersection of (Backbone Top-8) ∩ (SDT lane-positive) ∩ (HC is_high_conviction) — never weakened to force output, can legitimately be 0. Explosive Lane = 1-3 names from gate survivors, own formula (Room 32% + RR-at-current-price 30% + Activity 23% + Controlled-Volatility 15%), hard-reject list, regime-scaled minimum score (`EXPLOSIVE_MIN_SCORE_BY_REGIME`). Smart-Money Watch / Triple Confirmation / Divergence tags reuse `whitelist_accumulation_net_pct` (zero new cost). Long-Horizon Watch (multibagger) is a SEPARATE block, never blended into the Day 1-5 score.
- **Formula versioning discipline**: `BACKBONE_FORMULA_VERSION` (separate from `SCORING_FORMULA_VERSION`, Layer 1's own version marker) must be bumped on ANY threshold/weight/output-shape change — the cached `backbone_daily` partition carries this marker, and `load_backbone_daily_allow_stale()` forces a note (not a hard block) when the cache predates the running code. Never silently re-tune; log why in the version comment. Per the source doc: don't re-tune thresholds until 20-30 new trading days of forward data exist, except for genuine defects.

## RapidAPI IDX integration — shared discipline across both layers

- **500/month hard limit, 400 soft budget**, tracked per-endpoint in `rapidapi_idx_quota.json` (`engine/broker.py`, `_rapidapi_idx_quota_check_and_increment`). Burns fast if not disciplined — production burned ~30% of the monthly budget in the first 2 days live before same-day dedup was added.
- **Same-day dedup**: every nightly RapidAPI step (whitelist sweep, market-intelligence sweep, sentiment shortlist) checks a `trading_day_marker`-stamped cache before re-fetching — re-running `/eodscan` twice on the same trading day must not double-spend. `trading_night_index` (gates the every-2-nights/every-10th-night cadences) is day-aware, not call-count-aware, for the same reason.
- **"Missing = neutral, never penalize"**: any command reading RapidAPI-sourced fields must degrade gracefully when the field is `None` — never treat missing RapidAPI data as a negative signal, never hard-block a command on it being unavailable.
- **No live RapidAPI/on-demand fetch from bulk-scan commands** (`/check`, `/executiongate`) — both were switched to READ-ONLY same-day cache reuse after on-demand per-ticker fetches turned out to be the single biggest quota driver in production. If a new feature wants live broker data per-ticker, check whether the nightly sweep already covers it before adding a new live call.

## General conventions worth knowing before editing this codebase

- **Adaptive-percentile-vs-fixed-threshold**: when in doubt, prefer `core.percentile_rank`/`score_from_percentile` (or `engine/backbone.py`'s `percentile_rank_list` wrapper for plain lists) over a new hardcoded magic number — this is the house style for anything volatility/momentum-shaped.
- **Data freshness pattern**: `trading_day_marker` (calendar/trading-day match) + a formula-version marker on every cache partition; loaders return `(data, staleness_note)` and the convention is to SHOW stale data with a clear note rather than refuse outright (`load_daily_scan_cache_allow_stale`, `load_backbone_daily_allow_stale`, etc.) — never hard-block on staleness alone.
- **Module-import circular-dependency pattern**: `engine/legacy_core.py` ↔ `engine/nightly.py` ↔ `engine/market.py` ↔ `engine/backbone.py` ↔ `commands/*.py` all cross-reference each other. Always `import engine.X as x_engine` (module import), NEVER `from engine.X import name` — and never call `x_engine.something` at module load time, only inside function bodies. Breaking this reintroduces the circular-import failure this pattern exists to avoid.
- **REUSE over reinvent**: this codebase's own stated discipline (many docstrings say it explicitly) — before adding a new score/signal, check whether an existing sub-score already covers most of it (e.g., backbone's danger score reuses `_score_breakout_drop_risk_v4` rather than re-deriving MACD/ADX/RR penalties from scratch).
